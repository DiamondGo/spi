# sPi 0.3.2 — GitHub desktop updates

## New / 新增

- A background stable-release check on packaged startup and every six hours. A clickable **!** appears next to Settings when a newer version exists; Settings also offers manual checking. No modal interrupts work just because an update exists.
- Download, verify and install the package matching the running OS and architecture **directly from GitHub Releases, without npm**. Version, architecture, download size, progress, failures/retry, installation directory and launch command are visible in English/Chinese and all three themes.
- Installation is side-by-side and preserves the old runtime. Continue working while downloading; after installation, **Restart to apply** asks for explicit confirmation before closing local windows, agents and terminals. Save unsent drafts first. Saved histories, settings, window placement and remote pairings retain the same user profile.
- General Settings and update checks no longer mount remote credential probes. Open **Manage remote access** explicitly before checking the system credential store; unrelated Mac Keychain approval cannot block checking updates. Enabled-host recovery and remote operations keep mandatory credential protection.
- Update operations require an owning local main-frame window. Remote viewers/controllers and subframes cannot update or restart a paired computer.
- One canonical release manifest contains **Linux x64, Linux ARM64, macOS Apple Silicon and macOS Intel**. All four are built/tested natively before publication. Windows remains deferred. npm publication is not part of this release pipeline.

## Fix / 修复

`spi update` previously sent `Accept: application/octet-stream` to GitHub's JSON latest-release API, which returns HTTP 415. JSON metadata now uses `application/vnd.github+json`; archives retain the binary representation. Stable SemVer comparison, exact version/target archive layout, size, SHA-256, extraction containment and Mac signature verification are validated before activation.

## Upgrade from 0.3.1 / 从旧版升级

The old launcher cannot fix itself through its broken unversioned `spi update`, and the 0.3.1 GUI has no update controls. Bootstrap **once** using the new version-bound GitHub installer (requires Node.js 22.19+; no npm):

```bash
curl -fL https://github.com/DiamondGo/spi/releases/download/v0.3.2/install.sh -o /tmp/spi-install-0.3.2.sh
# Inspect the downloaded script before running it.
bash /tmp/spi-install-0.3.2.sh --version 0.3.2
```

Save drafts, fully quit the old app, then run `spi`. After this bootstrap, both the GUI updater and the managed `spi update` use the corrected GitHub-only path. Existing immutable npm versions remain unchanged; reinstalling `spi-agent-gui@0.3.1` still installs its old desktop version, not 0.3.2.

Alternatively download and verify the ZIP/tar.gz matching your architecture from this Release. Manual/extracted copies are not overwritten by in-app updates: they install a managed runtime and restart into it. Use the **exact launch command shown in Settings** afterward, not an old application copy or unrelated PATH command. If an unrelated `~/.local/bin/spi` exists, it is preserved and a private command is installed under the managed root.

## Safety and limitations / 边界

- macOS packages are **ad-hoc signed, not Developer ID signed or notarized**. Native signature integrity is checked, but Internet-download Gatekeeper trust is not claimed. Never disable protections or remove quarantine attributes.
- There is no automatic crash-health rollback. Previous complete managed runtimes are retained; `spi rollback` is available when the previous version is usable. Manually extracted old copies remain intact.
- Background checks contact the public GitHub release API without account credentials; network/rate-limit failures are shown in Settings and can be retried. They do not interrupt sessions or prove that an offline machine is up to date.
- The GUI preserves custom managed roots and protects a directly relaunched managed runtime from uninstall. No process-name-based killing, sudo, Pi configuration changes or npm authentication is needed.
- Source/installer/GUI tests run in isolated profiles. Native CI and public-download acceptance must pass before this candidate is described as published; evidence is recorded separately in `docs/verification.md`.
